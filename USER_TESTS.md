# User tests — 5–10 живых сессий с инженерами

Цель: **увидеть, как реальный инженер проходит путь без подсказок**, и собрать
данные для следующего roadmap. Не добавляем новые функции, пока тесты не
покажут, что существующее сложно понять.

## Кого приглашать

- 5–10 микс/мастер-инженеров: Gearspace, Twitter/X, личные контакты.
- По возможности — их же клиента (артист/A&R) для второй половины пути.
- Не выбирать только «технарей»: хотя бы пара инженеров без бэкграунда в
  софте (работают в основном в DAW и почте).

## Подготовка

```bash
make dev                # backend :8000 + frontend :5173
# demo: login demo/demo123 · sample review: http://localhost:5173/r/demo-review-token
# CLI: cd backend && ./soundhub --help
```

Для каждого участника создай **отдельную сессию** (их данные не должны
смешиваться) и приготовь 1–2 аудио-файла (wav) для загрузки.

## Единый сценарий (одинаковый для всех)

1. Создать сессию и **Client brief** (тип услуги, жанр, цель, дедлайн,
   deliverables, «что не менять»).
2. Отправить публичную ссылку (`/r/:token`) себе на второй экран/телефон.
3. Как клиент: оставить **voice note** и структурированный комментарий
   (шаблон → элемент → направление).
4. Отправить consolidated notes (submit round).
5. Как инженер: загрузить новую версию — **через CLI**:
   `./backend/soundhub push mix.wav --session <name> --message "v2: bass fixed"`.
6. Сделать **loudness-matched A/B** v1 ↔ v2.
7. Approve версию (клиент).
8. Создать release package → **QC preflight** → lock.
9. Выставить invoice → **Stripe checkout** → оплатить (тестовый режим).
10. Скачать delivery по ссылке `/d/:token`.
11. (Опционально) Request a change → quote → accept.

**Не помогать.** Допустимы только ответы «посмотри на страницу / попробуй
нажать» — без объяснения шагов.

## Что наблюдать (чек-лист)

- Где участник **задал вопрос** (запиши точный экран и формулировку).
- Где **не понял, куда нажать** (первый взгляд: что привлекло, что нет).
- Путаница в **ролях** (кто утверждает, чем reviewer отличается от approver).
- **Что делать после approval** — нашёл ли путь к package/delivery сам.
- Понятен ли **brief** клиенту (термины: LUFS, stems, watermark…).
- CLI: смог ли запустить push без чтения доки (читал ли `--help` вообще).

## Метрики (записывать в отчёт)

| Метрика | Как мерить |
|---|---|
| Time to first feedback | от открытия ссылки до первого комментария/voice note |
| % отправивших consolidated notes | submit round без напоминания |
| Число revision rounds | сколько раундов до approval |
| % approvals без ручных напоминаний | approve без того, что инженер пинговал |
| Time-to-payment | от invoice до оплаты checkout |
| Где просили помощи | список экранов/действий |

## Форма отчёта после каждого теста

```markdown
## Тест №N — <ник/роль участника>, <DAW>, <дата>

### Что сломалось / не работало
-

### Где пришлось объяснять (вопросы участника)
-

### Что назвали «важным»
-

### Что «не заметили» (фичи, которые не увидели сами)
-

### Метрики
- time-to-first-feedback:
- consolidated notes отправлены:
- раундов до approval:
- approval без напоминаний:
- time-to-payment:
- просили помощи (экраны):

### Вердикт: прошёл путь сам / с подсказками / не прошёл
```

## После всех тестов

1. Свести отчёты в один список «боли» по частоте.
2. Исправить **onboarding и public review** по топ-3 проблемам.
3. Только потом рассматривать: USDC, Max for Live review comments, REAPER.
4. Повторить цикл, когда исправления внедрены.

## Что НЕ тестируем сейчас

- USDC checkout, mainnet proofs, DAO, NFT-лицензии, marketplace — пока
  10+ инженеров не платят за текущий workflow.
